94.  [Route Parameters] How would you implement /books/:id?

Route parameters are dynamic parts of a URL. In /books/:id, the :id is a placeholder, so /books/42 gives id = '42'.

**Three steps:** define the route with `:id`, read the id in the component, then load the book.

**1. Define the route**

```typescript
{ path: 'books/:id', component: BookDetailComponent }
```

`:id` is a placeholder. For `/books/42`, the id is `'42'` (always a string).

**2. Read the id and load the book**

```typescript
export class BookDetailComponent implements OnInit {
  book?: Book;

  constructor(
    private route: ActivatedRoute,
    private bookService: BookService
  ) {}

  ngOnInit() {
    this.route.paramMap
      .pipe(
        map(params => Number(params.get('id'))),
        switchMap(id => this.bookService.getBook(id))
      )
      .subscribe(book => this.book = book);
  }
}
```

**3. Navigate to it**

```typescript
this.router.navigate(['/books', book.id]);   // goes to /books/42
```

**Why `paramMap` and not `snapshot`?**

- `snapshot.paramMap.get('id')` reads the id once, when the component is created.
- If the user goes from `/books/1` to `/books/2`, Angular **reuses the same component**, so the snapshot stays at 1.
- `paramMap` is an Observable that emits again on every change, so the page always shows the right book.
- `switchMap` cancels the old request if the id changes before it finishes.

**Things to mention in an interview**

- **Params are strings.** Convert with `Number()`.
- **Invalid id:** if the book is not found, redirect with `router.navigate(['/not-found'])`.
- **Alternative:** a resolver can load the book before the page opens, as in the earlier design.

**Short answer**

"I define `books/:id`, inject `ActivatedRoute`, and subscribe to `paramMap` instead of using the snapshot, because Angular reuses the component when only the id changes. I use `switchMap` to load the book for each id, and navigate with `router.navigate(['/books', id])`."

95.  [Query Parameters] How would you implement /books?category=java?

**What are query parameters?**

Query parameters are optional key-value pairs added to the end of a URL after a `?`. They describe *how* to show a page (filter, sort, page number), not *which* page to show.

```
/books?category=java&page=2&sort=title
  |      |             |        |
 path   key=value   key=value  key=value
```

- The path (`/books`) decides which component loads.
- The query params (`category`, `page`, `sort`) are extra settings the component can read.
- Separate pairs with `&`.
- Values are always strings.

**Why use them?**

- They are optional: `/books` and `/books?category=java` both work.
- The filter lives in the URL, so users can bookmark it, share it, and the browser Back button restores it.
- Refreshing the page keeps the filter.

**How to use them: 3 operations**

**1. Set them (navigate with params)**

```typescript
this.router.navigate(['/books'], {
  queryParams: { category: 'java', page: 1 }
});
// URL becomes /books?category=java&page=1
```

**2. Read them**

```typescript
this.route.queryParamMap.subscribe(params => {
  const category = params.get('category');       // 'java' or null
  const page = Number(params.get('page') ?? 1);  // 1 by default
});
```

**3. Change one and keep the rest**

```typescript
this.router.navigate([], {
  queryParams: { page: 2 },
  queryParamsHandling: 'merge'
});
// /books?category=java&page=1  becomes  /books?category=java&page=2
```

Without `merge`, the new params replace all the old ones, and `category` would be lost.

**Remove a param** by setting it to `null`:

```typescript
this.router.navigate([], {
  queryParams: { category: null },
  queryParamsHandling: 'merge'
});
// /books?category=java&page=2  becomes  /books?page=2
```

**Full example: category filter**

```typescript
export class BookGalleryComponent implements OnInit {
  books: Book[] = [];

  constructor(
    private route: ActivatedRoute,
    private router: Router,
    private bookService: BookService
  ) {}

  ngOnInit() {
    // runs every time the query params change
    this.route.queryParamMap
      .pipe(
        map(params => params.get('category')),
        switchMap(category => this.bookService.getBooks(category))
      )
      .subscribe(books => this.books = books);
  }

  selectCategory(category: string) {
    this.router.navigate([], {
      queryParams: { category, page: 1 },
      queryParamsHandling: 'merge'
    });
  }
}
```

**Flow:**
1. User clicks "Java", so `selectCategory('java')` runs.
2. The URL changes to `/books?category=java&page=1`.
3. `queryParamMap` emits the new params.
4. `switchMap` fetches Java books and the list updates.

**Route params vs query params**

| | Route param | Query param |
|---|---|---|
| Example | `/books/42` | `/books?category=java` |
| Purpose | identifies the resource | filters or options |
| Required? | yes | no |
| Defined in routes? | yes (`:id`) | no |
| Read with | `paramMap` | `queryParamMap` |

**Short answer**

"Query parameters are optional key-value pairs after the `?` in a URL, used for filters, sorting and pagination. 
They don't affect route matching. I set them with `router.navigate` and `queryParams`, read them from `route.queryParamMap`, 
and use `queryParamsHandling: 'merge'` to change one without losing the others. Because they live in the URL, 
the filtered view is bookmarkable, shareable and survives a refresh."

96.  [Multiple Query Parameters] How would you represent search, filter and sorting in the URL?

**Idea:** put each control in its own query parameter, so the whole state of the page is in the URL.

```
/books?search=spring&category=java&sort=price&order=asc&page=2
```

| Param | Purpose |
|---|---|
| `search` | text typed by the user |
| `category` | filter |
| `sort` | field to sort by |
| `order` | `asc` or `desc` |
| `page` | pagination |

**Set them**

```typescript
applyFilters() {
  this.router.navigate(['/books'], {
    queryParams: {
      search: 'spring',
      category: 'java',
      sort: 'price',
      order: 'asc',
      page: 1
    }
  });
}
```

**Change only one**

```typescript
changeSort(sort: string) {
  this.router.navigate([], {
    queryParams: { sort, page: 1 },
    queryParamsHandling: 'merge'   // keeps search and category
  });
}
```

**Read all of them and load books**

```typescript
ngOnInit() {
  this.route.queryParamMap
    .pipe(
      map(params => ({
        search: params.get('search') ?? '',
        category: params.get('category'),
        sort: params.get('sort') ?? 'title',
        order: params.get('order') ?? 'asc',
        page: Number(params.get('page') ?? 1)
      })),
      switchMap(filters => this.bookService.getBooks(filters))
    )
    .subscribe(books => this.books = books);
}
```

**Key points**

- **One source of truth:** the URL holds the state. Components read it and never keep a separate copy.
- **Defaults:** use `??` so a missing param still works (`/books` loads page 1, sorted by title).
- **Reset the page:** when search or a filter changes, set `page: 1`, otherwise you may land on an empty page.
- **Use `merge`:** so changing one param keeps the others.
- **Clean URLs:** set a param to `null` to remove it, e.g. clearing the search box.
- **Debounce search:** wait ~300 ms before updating the URL so each keystroke doesn't create a history entry.
- **Benefit:** the view is bookmarkable, shareable, survives refresh, and Back restores the previous filters.

**Short answer**

"I put search, filter, sort and page in separate query parameters like `/books?search=spring&category=java&sort=price&order=asc&page=2`. 
I update them with `router.navigate` using `queryParamsHandling: 'merge'`, read them from `queryParamMap` with defaults, 
and use `switchMap` to fetch the results. I reset `page` to 1 when filters change. Because the state lives in the URL, it is shareable, 
bookmarkable and survives a refresh."

97.  [Child Routes] When would Book Details need child routes?

**Goal:** a book detail page with three tabs, each with its own URL. The book header stays on screen and only the section below it changes.

```
/books/42            → Overview (default tab)
/books/42/reviews    → Reviews tab
/books/42/authors    → Authors tab
```

**1. Routes**

```typescript
// app.routes.ts
export const routes: Routes = [
  { path: 'books', component: BookGalleryComponent },
  {
    path: 'books/:id',
    component: BookDetailComponent,          // parent
    children: [
      { path: '', component: BookOverviewComponent },       // /books/42
      { path: 'reviews', component: BookReviewsComponent }, // /books/42/reviews
      { path: 'authors', component: BookAuthorsComponent }  // /books/42/authors
    ]
  }
];
```

The child paths are relative to the parent. The empty path `''` is the default tab.

**2. Parent component: loads the book once**

```typescript
export class BookDetailComponent implements OnInit {
  book?: Book;

  constructor(
    private route: ActivatedRoute,
    private bookService: BookService
  ) {}

  ngOnInit() {
    this.route.paramMap
      .pipe(
        map(params => Number(params.get('id'))),
        switchMap(id => this.bookService.getBook(id))
      )
      .subscribe(book => this.book = book);
  }
}
```

The parent's template has two things:
- The book header (title, cover, price) and tab links to `reviews` and `authors`.
- A `<router-outlet>`, which is the slot where the active child component appears.

**3. Child components: read the parent's id**

A child's own route has no `:id`, because it belongs to the parent. So the child reads it from `route.parent`.

```typescript
export class BookReviewsComponent implements OnInit {
  reviews: Review[] = [];

  constructor(
    private route: ActivatedRoute,
    private reviewService: ReviewService
  ) {}

  ngOnInit() {
    this.route.parent!.paramMap
      .pipe(
        map(params => Number(params.get('id'))),
        switchMap(id => this.reviewService.getReviews(id))
      )
      .subscribe(reviews => this.reviews = reviews);
  }
}
```

`BookOverviewComponent` and `BookAuthorsComponent` follow the same pattern with their own services.

**4. Navigating between tabs**

```typescript
// from inside any child or the parent
this.router.navigate(['reviews'], { relativeTo: this.route });
// or with an absolute path
this.router.navigate(['/books', 42, 'reviews']);
```

**How it flows**

1. The user opens `/books/42/reviews`.
2. The router matches the parent `books/:id` and the child `reviews`.
3. `BookDetailComponent` loads and fetches book 42.
4. `BookReviewsComponent` appears inside the parent's `<router-outlet>`.
5. The user clicks the Authors tab. The URL becomes `/books/42/authors`.
6. Only the child changes. The parent and its book data stay, so there is no reload and no extra book request.

**Why this design is good**

- **One load:** the book is fetched once, not once per tab.
- **Shared layout:** the header and tabs live in one place.
- **Real URLs:** each tab is bookmarkable and Back works.
- **Lazy loading:** you can lazy load a child with `loadComponent: () => import(...)`.

**Short answer**

"I make `books/:id` the parent with the header, tab links and a `router-outlet`. 
The overview, reviews and authors tabs are child routes, with overview as the empty-path default. 
The parent loads the book once, and children read the id from `route.parent.paramMap`. 
Each tab gets its own URL, and switching tabs only swaps the child."

98. [Lazy Loading] How would you lazy-load the Book feature?

app/
├── features/
│   ├── home/
│   ├── books/
│   ├── search/
│   ├── store/
│   │
│   └── admin/
│       ├── authors/
│       ├── books/
│       ├── categories/
│       ├── container/
│       ├── dashboard/
│       └── shared/
│
├── app.routes.ts
└── app.config.ts


**Lazy loading** means the browser downloads a feature's code only when the user first visits its route, instead of putting everything in the initial bundle. The first page loads faster.

**Folder structure**

```
src/app/
  app.routes.ts
  books/
    books.routes.ts
    book-gallery.component.ts
    book-detail.component.ts
    book.service.ts
```

**1. Main routes: use `loadChildren`**

```typescript
// app.routes.ts
export const routes: Routes = [
  { path: '', redirectTo: 'books', pathMatch: 'full' },
  {
    path: 'books',
    loadChildren: () =>
      import('./books/books.routes').then(m => m.BOOK_ROUTES)
  },
  { path: '**', component: NotFoundComponent }
];
```

No Book component is imported at the top of this file. The `import()` call is what tells the build to put the Book code in a separate file (a chunk).

**2. Feature routes: paths are relative to `books`**

```typescript
// books/books.routes.ts
export const BOOK_ROUTES: Routes = [
  { path: '', component: BookGalleryComponent },          // /books
  {
    path: ':id',
    component: BookDetailComponent,                       // /books/42
    children: [
      { path: '', component: BookOverviewComponent },
      { path: 'reviews', component: BookReviewsComponent }
    ]
  }
];
```

Because the parent path is already `books`, the feature uses `''` and `':id'`, not `'books'` and `'books/:id'`.

**3. Feature-only service**

```typescript
// books/book.service.ts
@Injectable()
export class BookService { /* ... */ }
```

To keep the service inside the lazy chunk, provide it in the feature routes:

```typescript
export const BOOK_ROUTES: Routes = [
  {
    path: '',
    providers: [BookService],     // created only when this feature loads
    children: [
      { path: '', component: BookGalleryComponent },
      { path: ':id', component: BookDetailComponent }
    ]
  }
];
```

**4. Lazy load a single component**

For one standalone component, use `loadComponent`:

```typescript
{
  path: 'about',
  loadComponent: () =>
    import('./about/about.component').then(m => m.AboutComponent)
}
```

**5. Preload in the background (optional)**

```typescript
// app.config.ts
provideRouter(routes, withPreloading(PreloadAllModules))
```

The app loads fast first, then downloads the lazy chunks while the user is idle. The next visit to `/books` is then instant.

**How it flows**

1. User opens `/`. Only the main bundle downloads.
2. User clicks to `/books`. The router sees `loadChildren` and downloads the Book chunk.
3. The router reads `BOOK_ROUTES` and shows `BookGalleryComponent`.
4. Later visits to `/books` reuse the already loaded chunk.

**Key points**

- **Don't import lazy components in `app.routes.ts`.** A normal `import` at the top puts them back in the main bundle and defeats lazy loading.
- **Good candidates:** admin area, rarely used features, large features.
- **Not for:** the home page or anything needed immediately.
- **Guards:** use `canMatch` to stop the chunk from downloading at all for unauthorized users, instead of `canActivate`, which still downloads it.
- **Check it works:** run `ng build` and look for separate chunk files in the output.

**Short answer**

"I move the Book feature into its own `books.routes.ts` 
and load it with `loadChildren: () => import('./books/books.routes').then(m => m.BOOK_ROUTES)`. 
The feature's paths are relative to `books`. This splits Book code into a separate chunk that downloads only on the first visit to `/books`, 
which shrinks the initial bundle. 
I can add `PreloadAllModules` to fetch it in the background, and use `canMatch` for guarded features."

99.  [CanActivate] How would you protect Add/Edit Book?

## What is `canActivate`?

`canActivate` is a **route guard**: a function that runs **before a route opens** and decides whether the user can enter. It returns:

| Return value 									| Meaning |
|---											|---		|
| `true` 										| Allow, the page opens |
| `false` 										| Block, the user stays where they are |
| A redirect (`router.createUrlTree([...])`) 	| Block and send the user somewhere else |

## Complete code (TypeScript only, no Signals)

### 1. `auth.service.ts`

```ts
import { Injectable } from '@angular/core';

export type Role = 'ADMIN' | 'LIBRARIAN' | 'CUSTOMER';

@Injectable({ providedIn: 'root' })
export class AuthService {
  // Plain properties. In a real app these come from your Spring Boot login/JWT.
  isLoggedIn = false;
  role: Role | null = null;

  login(role: Role): void {
    this.isLoggedIn = true;
    this.role = role;
  }

  logout(): void {
    this.isLoggedIn = false;
    this.role = null;
  }

  hasRole(...allowed: Role[]): boolean {
    return this.role !== null && allowed.includes(this.role);
  }
}
```

### 2. `auth.guard.ts`

```ts
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';
import { AuthService } from './auth.service';

// Protects Add Book and Edit Book.
// Rule: must be logged in AND be an ADMIN or LIBRARIAN.
export const bookEditGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);

  // 1. Not logged in -> go to login (remember where the user wanted to go)
  if (!auth.isLoggedIn) {
    return router.createUrlTree(['/login'], {
      queryParams: { returnUrl: state.url }
    });
  }

  // 2. Logged in with the right role -> allow
  if (auth.hasRole('ADMIN', 'LIBRARIAN')) {
    return true;
  }

  // 3. Logged in but wrong role (e.g. CUSTOMER) -> forbidden page
  return router.createUrlTree(['/forbidden']);
};
```

### 3. `app.routes.ts`

```ts

import { EditBookComponent } from './edit-book.component';
import { BookListComponent } from './book-list.component';

import { ForbiddenComponent } from './forbidden.component';

export const routes: Routes = [
  { path: '', redirectTo: 'books', pathMatch: 'full' },

  // Public pages (no guard)
  { path: 'books', component: BookListComponent },
  { path: 'login', component: LoginComponent },
  { path: 'forbidden', component: ForbiddenComponent },

  // Protected pages: the guard runs before the page opens
  { path: 'books/add', component: AddBookComponent, canActivate: [bookEditGuard] },
  { path: 'books/:id/edit', component: EditBookComponent, canActivate: [bookEditGuard] }
];
```

The components in the imports are your own pages. The guard doesn't depend on what is inside them.

### 4. `login.component.ts` (what happens after login)


## What the user experiences

| User 								| Result |
|---								|---|
| Not logged in 					| Sent to `/login`, then back to the page they wanted |
| Logged in as CUSTOMER 			| Sent to `/forbidden` |
| Logged in as ADMIN or LIBRARIAN 	| Page opens |

A guard only hides pages **in the browser**. Someone can still call the API directly, 
so Spring Boot must **also** check the role on the Add/Edit endpoints.

# Q100. [CanActivateChild] When would you use it for Admin routes?

## 1. What is `canActivateChild`?

`canActivateChild` is a **route guard** that you put on a **parent route**. It runs **before every child route opens** and decides allow or block.

**Analogy:** An office building has a main door and many rooms inside.

- `canActivate` is the guard at **one door**.
- `canActivateChild` is the guard standing **inside the building**, checking you at **every room** you enter.

## 2. The problem in the Admin area

The Admin area has several pages:

```
/admin/books
/admin/users
/admin/reports
```

**Without `canActivateChild`**, you must repeat the guard on every child:

```ts
children: [
  { path: 'books',   component: AdminBooksComponent,   canActivate: [adminGuard] },
  { path: 'users',   component: AdminUsersComponent,   canActivate: [adminGuard] },
  { path: 'reports', component: AdminReportsComponent, canActivate: [adminGuard] }
]
```

If you add a fourth page and forget the guard, that page is **unprotected**.

**With `canActivateChild`**, you write it **once** on the parent:

```ts
{
  path: 'admin',
  component: AdminLayoutComponent,
  canActivateChild: [adminChildGuard],   // protects ALL children
  children: [ ...books, users, reports... ]
}
```

A new child page is automatically protected.

## 3. Why not just put `canActivate` on the `admin` parent?

This is the key point. `canActivate` on the parent runs **only when the user enters `/admin` from outside**. 
After that, moving between `/admin/books` and `/admin/users` does **not** run the parent's `canActivate` again.

`canActivateChild` runs **every time the user moves to a child**. That matters when children have **different rules**, 
for example reports for ADMIN only.

## 4. Complete code (TypeScript only, no Signals)

### `auth.service.ts` (same as Q99)

```ts

@Injectable({ providedIn: 'root' })
export class AuthService {
  isLoggedIn = false;
  role: Role | null = null;

  login(role: Role): void {
    this.isLoggedIn = true;
    this.role = role;
  }

  logout(): void {
    this.isLoggedIn = false;
    this.role = null;
  }

  hasRole(...allowed: Role[]): boolean {
    return this.role !== null && allowed.includes(this.role);
  }
}
```

### `admin.guard.ts` (the guard)

```ts
import { inject } from '@angular/core';
import { CanActivateChildFn, Router } from '@angular/router';
import { AuthService, Role } from './auth.service';

export const adminChildGuard: CanActivateChildFn = (childRoute, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);

  // Step 1: not logged in -> send to login
  if (!auth.isLoggedIn) {
    return router.createUrlTree(['/login'], {
      queryParams: { returnUrl: state.url }
    });
  }

  // Step 2: which roles may open THIS child page?
  // Each child can say it in its route "data". If it says nothing,
  // the default is ADMIN and LIBRARIAN.
  const allowedRoles: Role[] = childRoute.data['roles'] ?? ['ADMIN', 'LIBRARIAN'];

  // Step 3: right role -> allow
  if (auth.hasRole(...allowedRoles)) {
    return true;
  }

  // Step 4: wrong role -> forbidden page
  return router.createUrlTree(['/forbidden']);
};
```

### `admin-layout.component.ts` (the parent page)

The parent needs a `router-outlet` so the child pages can appear inside it.

```ts
import { Component } from '@angular/core';
import { RouterOutlet } from '@angular/router';

@Component({
  selector: 'app-admin-layout',
  standalone: true,
  imports: [RouterOutlet],
  template: `<router-outlet />`
})
export class AdminLayoutComponent {}
```

### `app.routes.ts` (attach the guard to the parent)

```ts
import { Routes } from '@angular/router';
import { adminChildGuard } from './admin.guard';
import { AdminLayoutComponent } from './admin-layout.component';
import { AdminBooksComponent } from './admin-books.component';
import { AdminUsersComponent } from './admin-users.component';
import { AdminReportsComponent } from './admin-reports.component';

  { path: 'login', component: LoginComponent },

      // No "data": default rule, ADMIN or LIBRARIAN
      { path: 'books', component: AdminBooksComponent },

      // "data" says: ADMIN only
      { path: 'users', component: AdminUsersComponent, data: { roles: ['ADMIN'] } },
      { path: 'reports', component: AdminReportsComponent, data: { roles: ['ADMIN'] } }
    ]
  }
];
```

The child components (`AdminBooksComponent` and the others) are your own pages. The guard does not depend on what is inside them.

## 5. Step-by-step: a LIBRARIAN uses the Admin area

```
1. LIBRARIAN opens /admin/books
   guard runs → logged in ✅, books allows ADMIN + LIBRARIAN ✅ → page opens

2. LIBRARIAN clicks to /admin/users
   guard runs AGAIN → users allows ADMIN only ❌ → sent to /forbidden

3. LIBRARIAN goes back to /admin/books
   guard runs AGAIN → allowed ✅ → page opens
```

The guard runs on every move between children. A guard on the parent's `canActivate` could not do step 2.

## 6. What each user experiences

| User          | `/admin/books` | `/admin/users` | `/admin/reports` |
|---|---|---|---|
| Not logged in | Login page 	 | Login page 		| Login page |
| CUSTOMER 		| Forbidden  	 | Forbidden  		| Forbidden |
| LIBRARIAN 	| Opens 	 	 | Forbidden  		| Forbidden |
| ADMIN 		| Opens 		 | Opens 	 	 	| Opens |

## 7. canActivate vs canActivateChild

| 					| `canActivate` 				| `canActivateChild` |
|---				|---							|---					|
| Placed on 		| One route 					| A **parent** route |
| Runs 				| When that route opens 		| Before **each child** route opens |
| Best for 			| A single page (Add/Edit Book) | A whole section (Admin area) |
| Per-child rules 	| Must add a guard to each child| One guard reads each child's `data` |

## 8. When to use it

Use `canActivateChild` when:
- A parent route has **several children** that share the same protection (Admin area).
- Children need **different roles**, and you want to keep the rule in one place.
- You want **new child pages to be protected automatically**.

Use plain `canActivate` when you only protect **one page**.

## 9. Remember

A guard only hides pages **in the browser**. Someone can still call the API directly, 
so Spring Boot must **also** check roles on the admin endpoints.

## 10. Interview answer (30 seconds)

> "`canActivateChild` is a guard placed on a parent route. It runs before each of the parent's child routes opens. 
For the Admin area, I put it on the `admin` route so one guard protects books, users and reports. 
I don't need to repeat `canActivate` on each child, and any new child page is protected automatically. 
A guard on the parent's `canActivate` only runs when entering the Admin area, 
but `canActivateChild` runs on every move between child pages, so I can use route `data` to give each child its own allowed roles, 
like reports for ADMIN only. Because frontend checks can be bypassed, Spring Boot must enforce the same roles on the admin APIs."

# Q101. [CanDeactivate] How would you prevent losing unsaved Book changes?

## 1. What is `canDeactivate`?

`canDeactivate` is a **route guard** that runs when the user tries to **leave** a page. It asks: **"Is it OK to leave this page now?"**

**Analogy:** You are typing an email and click "Close". The app asks "Discard this draft?" before closing. `canDeactivate` is that question.

| Guard | Question |
|---|---|
| `canActivate` 		| Can the user **enter** this page? |
| `canDeactivate` | Can the user **leave** this page? |

## 2. The problem

A librarian edits a book's title, then accidentally clicks another link. Without a guard, the edit is **lost silently**.

## 3. The solution in 3 steps

1. The Edit Book component says "I can tell you whether it's safe to leave" (`canLeave()`).
2. A guard calls that method.
3. The route uses the guard with `canDeactivate`.

## 4. Complete code (TypeScript only, no Signals)

### `unsaved-changes.guard.ts`

```ts
import { CanDeactivateFn } from '@angular/router';
import { Observable } from 'rxjs';

// Any component that wants this protection must have a canLeave() method
export interface CanLeave {
  canLeave: () => boolean | Observable<boolean> | Promise<boolean>;
}

// Angular passes the component being left as the first argument
export const unsavedChangesGuard: CanDeactivateFn<CanLeave> = component => {
  return component.canLeave();
};
```

### `edit-book.component.ts`

```ts
import { Component, HostListener, inject } from '@angular/core';
import { ReactiveFormsModule, FormBuilder, Validators } from '@angular/forms';
import { ActivatedRoute, Router } from '@angular/router';
import { CanLeave } from './unsaved-changes.guard';
import { BookService } from './book.service';

@Component({
  selector: 'app-edit-book',
  standalone: true,
  imports: [ReactiveFormsModule],
  templateUrl: './edit-book.component.html'   // your own HTML, with [formGroup]="form"
})
export class EditBookComponent implements CanLeave {
  private fb = inject(FormBuilder);
  private router = inject(Router);
  private route = inject(ActivatedRoute);
  private bookService = inject(BookService);   // your existing service

  form = this.fb.nonNullable.group({
    title: ['', Validators.required],
    author: ['', Validators.required],
    price: [0]
  });

  save(): void {
    if (this.form.invalid) {
      return;
    }

    const id = Number(this.route.snapshot.paramMap.get('id'));

    this.bookService.updateBook(id, this.form.getRawValue()).subscribe(() => {
      // IMPORTANT: mark the form as saved BEFORE navigating,
      // otherwise the guard will ask "unsaved changes?" right after saving.
      this.form.markAsPristine();
      this.router.navigate(['/books']);
    });
  }

  // Called by the guard when the user tries to leave this page
  canLeave(): boolean {
    if (!this.form.dirty) {
      return true;   // nothing changed, leave freely
    }
    return confirm('You have unsaved changes. Do you really want to leave?');
  }

  // The guard does NOT cover closing the tab or refreshing the browser,
  // so this shows the browser's own warning for those cases.
  @HostListener('window:beforeunload', ['$event'])
  onBeforeUnload(event: BeforeUnloadEvent): void {
    if (this.form.dirty) {
      event.preventDefault();
    }
  }
}
```

`form.dirty` becomes `true` as soon as the user changes any field. After `markAsPristine()` it is `false` again.

### `app.routes.ts`

```ts
import { Routes } from '@angular/router';
import { bookEditGuard } from './auth.guard';
import { unsavedChangesGuard } from './unsaved-changes.guard';
import { EditBookComponent } from './edit-book.component';

export const routes: Routes = [
  {
    path: 'books/:id/edit',
    component: EditBookComponent,
    canActivate: [bookEditGuard],              // can the user ENTER? (Q99)
    canDeactivate: [unsavedChangesGuard]       // can the user LEAVE? (this question)
  }
];
```

## 5. Step-by-step: what happens

```
1. User opens Edit Book, changes the title
   form.dirty = true

2. User clicks a link to /books
   Angular runs canDeactivate → calls canLeave()
   dirty is true → confirm("unsaved changes...") appears
      User clicks Cancel → stays on the page ✅ (changes kept)
      User clicks OK     → leaves the page (changes discarded)

3. User clicks Save instead
   save succeeds → markAsPristine() → navigate to /books
   dirty is false → canLeave() returns true → leaves with no question
```

## 6. What each case does

| Situation 									| Result |
|---											|---			|
| Nothing changed 								| Leaves freely |
| Changed, then clicks another link 			| Confirm question appears |
| Changed, then clicks the browser Back button 	| Confirm question appears |
| Changed, then saves 							| Leaves freely |
| Changed, then refreshes or closes the tab 	| Browser's own warning (from `beforeunload`) |

## 7. Common mistake

Forgetting `this.form.markAsPristine()` after saving. The form is still "dirty", 
so the user sees "You have unsaved changes" **right after saving**.

## 8. Better than `confirm()`

`confirm()` works for a demo. In a real app you would show your own dialog. 
Because `canLeave()` can return an `Observable<boolean>`, 
the guard simply waits until the user clicks Yes or No in your dialog. The guard itself does not change.

## 9. Interview answer (30 seconds)

> "I use a `canDeactivate` guard on the Edit Book route. It runs when the user tries to leave the page. 
The Edit Book component has a `canLeave()` method that checks `form.dirty`. 
If nothing changed, it returns true. If there are unsaved changes, 
it asks the user to confirm, and returns false if they cancel so they stay on the page. 
After a successful save I call `markAsPristine()` so the guard doesn't ask again. 
The route guard doesn't cover closing the tab or refreshing, so I also add a `beforeunload` listener for those cases."

# Q102. [CanMatch] When would you use it instead of CanActivate?

## 1. What is `canMatch`?

`canMatch` is a **route guard** that runs **before Angular decides which route matches the URL**. 
If it returns `false`, Angular **skips that route as if it didn't exist** and tries the next route.

**Analogy:** You call a company and say "I need the dashboard."

- `canActivate`: the receptionist finds the Dashboard office, then says "You're not allowed in." You are **stopped**.
- `canMatch`: the receptionist checks who you are first, then **sends you to the right Dashboard office** for your role. 
The other offices are not even considered.

## 2. The key difference

| | `canActivate` | `canMatch` |
|---|---|---|
| When it runs 					| **After** the route is matched 		 | **While** matching the route |
| If `false` 					| User is **blocked** (redirect or stay) | Route is **skipped**, next route is tried |
| Same path, many routes? 		| No, the first match wins 				 | **Yes**, the first route whose guard passes wins |
| Lazy-loaded feature 			| Code may still be downloaded 			 | Code is **never downloaded** if `false` |

## 3. When I would use `canMatch` instead of `canActivate`

1. **Same URL, different page per role.** `/dashboard` shows one page to ADMIN, another to LIBRARIAN, another to CUSTOMER.
2. **Lazy-loaded Admin feature.** Customers should not even download the Admin code.
3. **Hide that a page exists.** A CUSTOMER visiting `/admin` gets "Not found" instead of "Forbidden", so they can't tell the page exists.

If you only want to **block** a page and show a message, `canActivate` is the right choice (like Q99).

## 4. Complete code (TypeScript only, no Signals)

Uses the same `AuthService` as Q99.

### `role-match.guard.ts`

```ts
import { inject } from '@angular/core';
import { CanMatchFn } from '@angular/router';
import { AuthService, Role } from './auth.service';

// A small "guard factory": give it roles, it returns a guard.
// Returns true -> this route can match
// Returns false -> Angular skips this route and tries the next one
export const hasRole = (...roles: Role[]): CanMatchFn => () => {
  const auth = inject(AuthService);
  return auth.isLoggedIn && auth.hasRole(...roles);
};
```

### `app.routes.ts`

```ts
import { Routes } from '@angular/router';
import { hasRole } from './role-match.guard';
import { AdminDashboardComponent } from './admin-dashboard.component';
import { LibrarianDashboardComponent } from './librarian-dashboard.component';
import { CustomerDashboardComponent } from './customer-dashboard.component';
import { LoginComponent } from './login.component';
import { NotFoundComponent } from './not-found.component';

export const routes: Routes = [
  { path: 'login', component: LoginComponent },

  // EXAMPLE 1: same path "dashboard", three routes.
  // Angular tries them from top to bottom. The first canMatch that passes wins.
  { path: 'dashboard', canMatch: [hasRole('ADMIN')],     component: AdminDashboardComponent },
  { path: 'dashboard', canMatch: [hasRole('LIBRARIAN')], component: LibrarianDashboardComponent },
  { path: 'dashboard', canMatch: [hasRole('CUSTOMER')],  component: CustomerDashboardComponent },

  // EXAMPLE 2: lazy-loaded Admin feature.
  // If canMatch is false, the admin code is never downloaded.
  {
    path: 'admin',
    canMatch: [hasRole('ADMIN')],
    loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES)
  },

  // Anything that did not match above ends up here
  { path: '**', component: NotFoundComponent }
];
```

### `admin/admin.routes.ts` (the lazy-loaded feature)

```ts
import { Routes } from '@angular/router';
import { AdminBooksComponent } from './admin-books.component';
import { AdminUsersComponent } from './admin-users.component';

export const ADMIN_ROUTES: Routes = [
  { path: 'books', component: AdminBooksComponent },
  { path: 'users', component: AdminUsersComponent }
];
```

## 5. Step-by-step: what happens

**User opens `/dashboard`:**

| User 			| Route 1 (ADMIN) 	| Route 2 (LIBRARIAN) 	| Route 3 (CUSTOMER) 	| Result |
|---			|---				|---					|---					|---				|
| ADMIN 		| ✅ matches 		| 						| 						| Admin dashboard |
| LIBRARIAN 	| ❌ skipped 		| ✅ matches 			| 						| Librarian dashboard |
| CUSTOMER 		| ❌ skipped 		| ❌ skipped 			| ✅ matches 			| Customer dashboard |
| Not logged in | ❌ 				| ❌ 					| ❌ 					| Falls to `**`: Not Found |

**User opens `/admin`:**

```
ADMIN    → canMatch true  → Admin code is downloaded → page opens
CUSTOMER → canMatch false → route skipped → Admin code NOT downloaded → Not Found
```

## 6. Why not `canActivate` here?

With `canActivate`, you could not have three routes on the same `/dashboard` path. 
Angular would match the **first** one and stop, so a CUSTOMER would be blocked from the Admin dashboard instead of being shown their own.

For the lazy-loaded Admin feature, `canMatch` also **prevents the download** of code the user should never see. 
`canMatch` replaces the old `canLoad` guard, which is now deprecated.

## 7. Use both together

They are not rivals. A common setup is `canMatch` to pick the route, then `canActivate` for extra checks:

```ts
{
  path: 'admin',
  canMatch: [hasRole('ADMIN')],           // is this route even for this user?
  canActivate: [someOtherGuard],          // extra check after matching
  loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES)
}
```

## 8. Remember

Hiding code in the browser is not security. Spring Boot must still check roles on the admin APIs.

## 9. Interview answer (30 seconds)

> "`canActivate` runs after a route is matched and blocks the user if the check fails. `canMatch` runs during matching, 
and if it returns false, Angular skips that route and tries the next one. I use `canMatch` 
when the same URL should show different pages by role, like a `/dashboard` for ADMIN, LIBRARIAN and CUSTOMER. 
I also use it on lazy-loaded features like Admin, so users without the role never download that code, 
and they get Not Found instead of Forbidden. It replaces the old `canLoad`. 
I still use `canActivate` when I just want to block a page and redirect to login or a forbidden page."

# Q103. [Route Resolver] When would you resolve Book Details before navigation?

## 1. What is a route resolver?

A resolver is a function that **loads data before the page opens**. Angular waits for the data to arrive, and only then shows the page.

**Analogy:** A restaurant brings your food **before** you sit down, so you never stare at an empty table. 
A resolver fetches the book **before** the Book Details page appears.

## 2. The problem without a resolver

You load the book in `ngOnInit`:

```
1. User clicks a book
2. Book Details page opens immediately (empty)
3. API call runs...
4. Data arrives, page fills in
```

The user sees an **empty page or flicker**. If the book doesn't exist (404), they first see the empty page and **then** an error.

## 3. The solution with a resolver

```
1. User clicks a book
2. Angular runs the resolver (API call), the user stays on the old page
3. Data arrives
4. Book Details page opens already filled ✅
```

If the book doesn't exist, the user is sent to a Not Found page and **never sees an empty Book Details page**.

## 4. When I would use it for Book Details

- The page **cannot show anything useful** without the book.
- You want to handle **404 before** the page opens.
- You want the component code simple: it just reads the data and never worries about loading.

## 5. Complete code (TypeScript only, no Signals)

### `book.model.ts`

```ts
export interface Book {
  id: number;
  title: string;
  author: string;
  price: number;
}
```

### `book.service.ts`

```ts
import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { Book } from './book.model';

@Injectable({ providedIn: 'root' })
export class BookService {
  private http = inject(HttpClient);

  getBook(id: number): Observable<Book> {
    return this.http.get<Book>(`/api/books/${id}`);
  }
}
```

### `book.resolver.ts` (the resolver)

```ts
import { inject } from '@angular/core';
import { ResolveFn, Router } from '@angular/router';
import { EMPTY, catchError } from 'rxjs';
import { Book } from './book.model';
import { BookService } from './book.service';

export const bookResolver: ResolveFn<Book> = route => {
  const bookService = inject(BookService);
  const router = inject(Router);

  // Read :id from the URL (/books/5 -> 5)
  const id = Number(route.paramMap.get('id'));

  return bookService.getBook(id).pipe(
    catchError(() => {
      // Book not found or API failed -> go to Not Found page
      router.navigate(['/not-found']);
      return EMPTY;   // EMPTY cancels the original navigation
    })
  );
};
```

### `app.routes.ts` (attach it with `resolve`)

```ts
import { Routes } from '@angular/router';
import { bookResolver } from './book.resolver';
import { BookDetailsComponent } from './book-details.component';
import { NotFoundComponent } from './not-found.component';

export const routes: Routes = [
  {
    path: 'books/:id',
    component: BookDetailsComponent,
    resolve: { book: bookResolver }     // "book" is the key the component reads
  },
  { path: 'not-found', component: NotFoundComponent }
];
```

### `book-details.component.ts` (reads the resolved data)

```ts
import { Component, inject } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { ActivatedRoute } from '@angular/router';
import { Book } from './book.model';

@Component({
  selector: 'app-book-details',
  standalone: true,
  template: `` // your own HTML goes here
})
export class BookDetailsComponent {
  private route = inject(ActivatedRoute);

  book!: Book;

  constructor() {
    // The book is ALREADY loaded when this component is created.
    // No loading flag, no API call, no null checks.
    this.route.data.pipe(takeUntilDestroyed()).subscribe(data => {
      this.book = data['book'];
    });
  }
}
```

## 6. Step-by-step: what happens

**Book exists (`/books/5`):**

```
1. User clicks book 5
2. Resolver calls GET /api/books/5
3. Book arrives → Angular opens BookDetailsComponent
4. Component reads data['book'] → page shows the full book immediately
```

**Book does not exist (`/books/999`):**

```
1. User clicks book 999
2. Resolver calls GET /api/books/999 → 404 error
3. catchError → router.navigate(['/not-found'])
4. Not Found page opens. Book Details never appeared.
```

## 7. Resolver vs loading in `ngOnInit`

| | Resolver | Load in `ngOnInit` |
|---|---|---|
| Page opens 			| **After** data arrives 				| **Before** data arrives |
| Empty page or flicker | No | Yes (unless you add a spinner) 	|
| 404 handling 			| Before the page shows 				| After the page shows |
| Component code 		| Simple, just reads data 				| Needs loading and error state |
| While waiting 		| User stays on the **old page** 		| User sees the new page with a spinner |

## 8. When NOT to use a resolver

If the API is **slow**, the user clicks and **nothing seems to happen** until the data arrives, 
because they stay on the old page. For slow calls, 
it is better to open the page and show a spinner (`ngOnInit` approach), or show a global loading bar using router events.

Use a resolver when the call is **fast and the page needs the data to make sense**, like a single Book Details call.

## 9. One detail to remember

The same component is reused when the URL changes from `/books/1` to `/books/2`. 
That is why the component **subscribes to `route.data`** instead of reading `route.snapshot.data` once. 
The subscription updates `book` each time the resolver finishes.

## 10. Interview answer (30 seconds)

> "A route resolver is a function that loads data before a route activates. 
Angular waits for it to finish, then opens the component with the data already available. 
For Book Details I would use a resolver so the page never appears empty or flickers, 
and so a missing book (404) can be handled before the page shows, by redirecting to a Not Found page. 
The component simply reads the data from `route.data`. I avoid resolvers for slow APIs, 
because the user stays on the old page with no feedback. In that case I load the data in the component and show a spinner."

104. [Route Data] How would you pass metadata to Admin routes?

**Route data** is a static object attached to a route with the `data` property. Use it for fixed metadata such as page title, 
required role, or breadcrumb label. 
It does not change per visit, which is different from route params.

**1. Add `data` to the admin routes**

```typescript
// admin/admin.routes.ts
export const ADMIN_ROUTES: Routes = [
  {
    path: 'books/new',
    component: BookFormComponent,
    data: { title: 'Add Book', roles: ['ADMIN'], breadcrumb: 'New Book' }
  },
  {
    path: 'books/:id/edit',
    component: BookFormComponent,
    data: { title: 'Edit Book', roles: ['ADMIN', 'EDITOR'], breadcrumb: 'Edit Book' }
  }
];
```

**2. Read it in a component**

```typescript
export class BookFormComponent implements OnInit {
  title = '';

  constructor(private route: ActivatedRoute) {}

  ngOnInit() {
    this.route.data.subscribe(data => this.title = data['title']);
  }
}
```

**3. Read it in a guard (the most common use)**

The guard checks the roles listed in the route's data, so one guard works for every route.

```typescript
export const roleGuard: CanActivateFn = (route) => {
  const auth = inject(AuthService);
  const router = inject(Router);
  const allowed: string[] = route.data['roles'] ?? [];

  return allowed.includes(auth.role())
    ? true
    : router.createUrlTree(['/books']);
};
```

Attach it once to the parent:

```typescript
{
  path: 'admin',
  canActivate: [roleGuard],
  data: { roles: ['ADMIN'] },
  loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES)
}
```

**4. Page title without code**

Angular has a built-in `title` property on routes:

```typescript
{ path: 'books/new', component: BookFormComponent, title: 'Add Book' }
```

It sets the browser tab title automatically.

**Key points**

- **Static only:** `data` is fixed at build time. For values loaded from an API, use a `resolve`.
- **Inheritance:** child routes inherit parent `data` only when the parent has an empty path or a componentless route, or when you set `paramsInheritanceStrategy: 'always'`.
- **Typed access:** `data['roles']` is untyped, so define an interface or constants for the keys to avoid typos.

**Short answer**

"I attach metadata with the `data` property on the route, for example `data: { roles: ['ADMIN'], title: 'Add Book' }`. 
A guard reads it from `route.data` to decide access, and components read it from `ActivatedRoute.data`. It is for static values; 
for dynamic values I use a resolver."

105. [Route-level Providers] Why might BookGallery need them?
**Route-level providers** are services declared in a route's `providers` array. Angular creates them when the route is first activated, in an injector that belongs to that route and its children, not in the app-wide root injector.

```typescript
{
  path: 'books',
  providers: [BookService, BookFilterStore],
  children: [
    { path: '', component: BookGalleryComponent },
    { path: ':id', component: BookDetailComponent }
  ]
}
```

**Why BookGallery might need them**

1. **Scoped state.** A `BookFilterStore` holding search, category and sort should exist only while the user is in the Books area. With route-level providers, the state lives with the feature and is cleaned up when the route's injector is destroyed (for lazy routes, it stays for the app's life, but it is still isolated from other features).

2. **Lazy loading.** Services provided on a lazy route are bundled into that route's chunk. The root bundle stays small, and the service is created only when the user first visits `/books`.

3. **Sharing within the feature only.** The gallery, the detail page and their children all get the same `BookService` instance. Unrelated features such as Admin cannot accidentally depend on it.

4. **Different configuration per area.** The same class can behave differently in different routes.

```typescript
{
  path: 'books',
  providers: [{ provide: PAGE_SIZE, useValue: 12 }]
},
{
  path: 'admin',
  providers: [{ provide: PAGE_SIZE, useValue: 50 }]
}
```

5. **Easier testing and replacement.** You can swap a service for one route (a mock or a different implementation) without touching the rest of the app.

**Compare with `providedIn: 'root'`**

| | `providedIn: 'root'` | Route-level `providers` |
|---|---|---|
| Instance | one for the whole app | one per route injector |
| Created | when first injected | when the route is first activated |
| In bundle | main (or where used) | the lazy route's chunk |
| Best for | app-wide services (auth, http wrappers) | feature-specific services and state |

**Short answer**

"BookGallery may need route-level providers so services like `BookService` or a filter store are scoped to the Books feature. 
They are created only when the route is first activated, live in the lazy chunk, are shared by the gallery and detail pages, 
and stay isolated from other features. I would keep truly global services, like auth, as `providedIn: 'root'`."

107. [Preloading] When would you preload the Books feature?

**Preloading** means downloading a lazy-loaded chunk in the background, after the app has started, before the user clicks to it. The first page stays fast, and later navigation feels instant.

**When to preload the Books feature**

- **It is the main feature.** Almost every visitor goes from the home page to `/books`, so downloading it early costs little and saves a wait.
- **The chunk is large.** A big chunk causes a visible delay on the first click.
- **Users are on good connections.** Preloading uses bandwidth, so it suits Wi-Fi or desktop more than slow mobile data.
- **The user is likely to go there next**, such as a login page where Books is always the next stop.

**When not to preload**

- Rarely used areas like Admin. Most users never need them.
- Very small chunks, where lazy loading already feels instant.
- Slow or metered connections.

**1. Preload everything**

```typescript
// app.config.ts
provideRouter(routes, withPreloading(PreloadAllModules))
```

The app loads first. Then every lazy chunk downloads in the background.

**2. Preload only chosen routes (custom strategy)**

Mark the route:

```typescript
{
  path: 'books',
  data: { preload: true },
  loadChildren: () => import('./books/books.routes').then(m => m.BOOK_ROUTES)
},
{
  path: 'admin',
  loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES)
}
```

Write the strategy:

```typescript
@Injectable({ providedIn: 'root' })
export class SelectivePreloadStrategy implements PreloadingStrategy {
  preload(route: Route, load: () => Observable<any>): Observable<any> {
    return route.data?.['preload'] ? load() : of(null);
  }
}
```

Register it:

```typescript
provideRouter(routes, withPreloading(SelectivePreloadStrategy))
```

Now Books downloads in the background and Admin only downloads when visited.

**How it flows**

1. The user opens the app. Only the main bundle downloads.
2. After the first navigation finishes, the router preloads `books`.
3. The user clicks to `/books`. The chunk is already there, so it opens instantly.

**Key points**

- **Preloading starts after the initial navigation**, so it never slows the first page.
- **`canMatch` guards** can skip preloading for users who can't access a route.
- **Default is no preloading.** Lazy chunks download only on first visit.

**Short answer**

"I would preload Books because it is the main feature most users open next, 
so downloading it in the background makes the first click instant without slowing the first page. 
I'd use `PreloadAllModules` for a small app, or a custom strategy with `data: { preload: true }` 
so only Books is preloaded and rarely used areas like Admin stay lazy."
